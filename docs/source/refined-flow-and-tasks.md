## MVP System Flow

### 1. Household Setup

The MVP will be tested in a sample household using a **Shelly EM Gen3 with a CT clamp** installed on the main electricity supply.

The Shelly will measure the household's total electricity consumption at high frequency, ideally around **1-second intervals**.

The Shelly does not identify individual appliances itself. It only tells us how much electricity the whole house is using at each point in time.

**Basic flow:**

House electricity → CT clamp measures total load → Shelly records the readings → Data is sent through the household Wi-Fi → Our backend receives and stores the data

A laptop does not need to remain inside the house. The goal is for the Shelly to communicate directly with our backend through the internet.

### 2. Customer-Facing Website

For the MVP, we will build a **web platform rather than a full mobile app**.

The customer will log into the website and complete an initial household setup.

The website will collect information such as:

- major appliances in the home
- appliance type
- approximate/rated wattage if known
- make/model if available
- common appliance settings or modes
- electric or gas hot water
- heating/cooling systems
- solar
- battery
- EV
- household/occupancy information

This information narrows down what appliances the system needs to look for.

For example, if the household does not own an EV or dryer, the model does not need to consider those appliances when explaining a large electricity event.

### 3. Initial Appliance Inventory

The customer creates a list such as:

Kettle → 2200 W Microwave → 1200 W Washing machine → 2000 W Oven → 2400 W Dishwasher → 1800 W

These wattages are **starting information only**.

We cannot assume that an appliance always uses its rated wattage because many appliances have:

- multiple operating modes
- multiple stages
- heating cycles
- motors
- variable-speed components
- different user settings

Therefore, the wattage helps narrow down possible appliances but is not used as the sole identification method.

### 4. Guided Appliance Calibration

The website will guide the customer through operating important appliances individually.

Example:

**Step 1:** Make sure the kettle is off. **Step 2:** Press "Start Calibration". **Step 3:** Turn the kettle on normally. **Step 4:** Allow it to finish. **Step 5:** Repeat several times if required.

While this happens, the Shelly continuously records the whole-house electricity signal.

Because we know exactly when the customer turned the appliance on, we can label that electricity pattern:

**This signal = this household's kettle.**

This creates household-specific training data.

### 5. Different Calibration Approaches

Different appliances require different approaches.

**Simple appliances**

Examples:

- kettle
- toaster
- heater
- some dryers

These can usually be calibrated by turning them on and off several times.

We capture:

- increase in wattage
- duration
- stability of the load
- ON/OFF transition

**Multi-stage appliances**

Examples:

- washing machine
- dishwasher

The customer will start a normal cycle and tell the website:

**"Washing machine started now."**

The system then records the electricity pattern over the complete cycle.

Instead of learning one wattage, the system learns a sequence such as:

motor → heating → lower load → spin → pump → off

Different programs may produce different patterns.

For the MVP, we should initially focus on the customer's **most commonly used setting** rather than trying to learn every washing-machine program.

**Variable-load appliances**

Examples:

- air conditioners
- inverter refrigerators
- heat pumps
- induction cooktops

These do not have simple fixed ON/OFF signatures.

For these appliances we may rely more heavily on:

- longer-term patterns
- operating ranges
- duration
- time of day
- weather
- previous appliance behaviour
- machine learning

These will likely be harder and may be partially deferred during the MVP.

### 6. Data Processing

The Shelly continues producing approximately 1-second readings.

For example:

10:00:01 → 420 W 10:00:02 → 425 W 10:00:03 → 421 W 10:00:04 → 2620 W 10:00:05 → 2618 W

We retain all individual 1-second measurements.

The readings can be transmitted to the backend in batches, for example every 5–30 seconds, without reducing the underlying 1-second resolution.

The backend stores the time-series data for analysis.

### 7. Event Detection

The first analysis layer detects meaningful changes in electricity consumption.

Example:

House = 420 W

Suddenly:

420 W → 2610 W

Change:

+2190 W

The system records an event.

It then analyses characteristics such as:

- size of the wattage increase
- size of the wattage decrease
- duration
- repetition
- cycling
- time of day
- behaviour before and after the event

This provides candidate appliance events before more advanced NILM/ML analysis is applied.

### 8. Appliance Identification

The system combines several sources of information:

**Whole-house signal**

**Customer appliance inventory**

**Rated appliance wattage**

**Household-specific calibration**

**Known NILM patterns**

**Duration and operating behaviour**

**Historical usage**

**Machine learning / probabilistic matching**

The system then estimates which appliance most likely produced the event.

For example:

Detected event:

+2150 W Duration: 145 seconds Stable load Household owns 2200 W kettle Previously calibrated kettle ≈ 2130–2190 W

Result:

**Likely kettle**

### 9. Existing NILM Models

We are not building the entire intelligence system from scratch.

The data scientist will investigate and benchmark existing NILM approaches including:

- event/edge detection
- rule-based identification
- combinatorial optimisation
- HMM/FHMM probabilistic models
- Sequence-to-Point
- Sequence-to-Sequence
- CNN/RNN approaches
- transfer learning
- household-specific fine-tuning

Existing NILM provides a general starting point.

Our additional value is combining NILM with:

**household information + guided calibration + personalised learning + customer confirmation.**

### 10. Human-in-the-Loop Confirmation

When the system is uncertain, the website can ask the customer.

Example:

**"We detected a 1.8 kW appliance running between 7:15 PM and 8:05 PM. Was this your dishwasher?"**

Options:

Yes No Choose another appliance I don't know

If the customer confirms the dishwasher, that becomes another labelled example.

Over time, the system builds a stronger understanding of that particular household.

The customer therefore does not need to calibrate every possible appliance during onboarding.

### 11. Household Learning Over Time

The system gradually builds a personalised appliance profile.

For example:

**Kettle**

Typical increase: 2.1–2.2 kW Typical duration: 1–3 minutes Confidence: high

**Washing machine**

Typical cycle: 45–70 minutes Multiple power states Most common program learned Confidence: medium/high

**Air conditioner**

Highly variable load Weather dependent Long-duration behaviour Confidence: lower initially

The system becomes increasingly personalised as more data and confirmations are collected.

### 12. Energy Disaggregation Output

The backend then converts appliance detections into estimated consumption.

Example monthly output:

Total household electricity: 500 kWh

Estimated:

Air conditioning → 150 kWh Hot water → 100 kWh Oven/cooking → 65 kWh Washing machine → 25 kWh Dishwasher → 20 kWh Kettle → 12 kWh Other/unknown → 128 kWh

We should expect to maintain an **unknown/other category**, particularly during the MVP, rather than pretending every watt can be perfectly assigned.

### 13. Customer Dashboard

The website can show:

**Energy breakdown**

Estimated electricity consumption by appliance/category.

**Cost breakdown**

Estimated cost based on tariff and time of usage.

**Usage history**

When appliances were estimated to have operated.

**Unusual usage**

Examples:

"Your hot-water electricity consumption is significantly higher than usual."

**Recommendations**

Examples:

"Your dishwasher frequently operates during your expensive tariff period."

**Confidence**

Where appropriate, estimates can be shown as:

High confidence Medium confidence Low confidence

rather than presenting uncertain NILM results as exact measurements.

## MVP Principle

The MVP is **not trying to perfectly identify every appliance automatically**.

The initial goal is to determine whether we can reliably identify a smaller number of important/high-consumption appliances by combining:

**high-resolution whole-house data + existing NILM methods + household information + guided calibration + user feedback.**

If this works, we can progressively expand the number of supported appliances and introduce more sophisticated ML later.

## MVP System Flow Diagram

### 1. Simple Flow Diagram

**Household Main Supply** ↓ **CT Clamp on Main Wire** ↓ **Shelly EM Gen3** ↓ **Home Wi-Fi** ↓ **Raspberry Pi / Local Collector** ↓ **Cloud Backend / Database** ↓ **Event Detection + NILM / ML Analysis** ↓ **Appliance Estimates + Cost / Usage Insights** ↓ **Customer Website Dashboard** ↓ **User Confirmation / Calibration Feedback** ↓ **Improved Household Model**

### 2. What each step means

**Household Main Supply**

This is the incoming electricity line for the house.

**CT Clamp on Main Wire**

The CT clamp goes around the main wire and measures current flow. This is the sensor piece. It comes with the Shelly EM Gen3 package.

**Shelly EM Gen3**

The Shelly receives the CT reading, combines it with voltage information, and produces whole-house electricity measurements such as watts, current, voltage, and power factor.

**Home Wi-Fi**

The Shelly uses the home's Wi-Fi to communicate locally.

**Raspberry Pi / Local Collector**

This is our MVP bridge device. Its job is to:

- continuously collect high-resolution readings from Shelly
- timestamp them
- temporarily store them if internet drops
- send them to our cloud

Important: the Pi is **not** measuring electricity itself. It is just collecting data from the Shelly.

**Cloud Backend / Database**

This stores the incoming data from the household.

**Event Detection + NILM / ML Analysis**

This is the intelligence layer. It:

- detects changes in power usage
- compares them against appliance inventory
- uses calibration data
- applies NILM / ML methods to estimate what appliance likely caused the usage

**Appliance Estimates + Cost / Usage Insights**

This is where we generate outputs such as:

- estimated appliance/category consumption
- possible cost breakdown
- unusual usage
- efficiency insights

**Customer Website Dashboard**

This is the user-facing platform where the customer can:

- see usage breakdowns
- enter household/appliance details
- complete setup and calibration
- review insights

**User Confirmation / Calibration Feedback**

The user helps the system learn by:

- entering appliance list and wattage
- running appliances one at a time during setup
- confirming uncertain detections

This creates household-specific labeled data.

**Improved Household Model**

The system becomes more tailored to that specific household over time.

### 3. Customer Setup Flow

**Customer opens website** ↓ **Creates household profile** ↓ **Enters appliance list + rated wattage + home details** ↓ **Follows guided calibration for key appliances** ↓ **System records signatures from Shelly data** ↓ **Model begins household-specific appliance detection**

### 4. Calibration Flow

**User selects appliance on website** ↓ **Website says "Start Calibration"** ↓ **User turns appliance on** ↓ **Shelly captures whole-house power change** ↓ **Pi forwards readings to cloud** ↓ **System labels that pattern as that appliance** ↓ **Repeat for key appliances**

### 5. One-line summary

Shelly measures total household electricity, Raspberry Pi collects and forwards the data, the cloud analyses it using NILM/ML plus customer inputs, and the website shows insights while collecting feedback to improve the model.

## Things we can do now

1. **Build the data pipeline skeleton** Create the format the Shelly data will eventually enter, for example: timestamp, watts, voltage, current, power factor. Use fake or public NILM data for now.
2. **Build basic event detection** Have the data scientist create logic that detects meaningful changes in power, such as 450 W → 2,600 W, and records the size and duration of the event.
3. **Test existing NILM models on public datasets** Use datasets such as UK-DALE or REFIT and test simple approaches first: rules/event matching, then something like Seq2Point. The purpose is to understand what works before our own data arrives.
4. **Design the appliance-calibration process** Decide exactly what the user will do, for example: select “kettle” → press Start → turn kettle on → system records the period → repeat. Also define different procedures for simple appliances versus washers/dishwashers with full cycles.
5. **Build the basic web interface** It does not need to look polished yet. Just create screens for household setup, appliance list, rated wattage, Start Calibration, and confirmation such as “Was this your washing machine?”
6. **Prepare the Shelly collector software** Write the Raspberry Pi/local collector code now so that once the Shelly is installed, we only need to connect it, enter its local address/credentials, and start receiving roughly 1-second readings.

The **highest-priority work right now** is therefore:

**data scientist → event detection + NILM testing + calibration methodology** **developer → backend data pipeline + simple website + Shelly/Pi collector**
